# auto-destination-id Specification

## Purpose
Define how destination IDs are auto-generated by the backend and how the system handles destinations as address-only entities.

## ADDED Requirements

### Requirement: Auto-generate destination ID

The system SHALL auto-generate a unique ID for each destination when it is added to a cluster. The ID format SHALL be `{clusterId}-{sequence}`, where the sequence is a monotonically increasing integer within the cluster scope.

#### Scenario: New cluster with destinations IDs
- **WHEN** user creates a cluster with destinations `["http://srv1:8080", "http://srv2:8080"]`
- **THEN** destinations SHALL get IDs `{clusterId}-1` and `{clusterId}-2` respectively

#### Scenario: Add destination to existing cluster
- **WHEN** user adds destination `http://srv3:8080` to a cluster that already has `{clusterId}-1` and `{clusterId}-2`
- **THEN** the new destination SHALL get ID `{clusterId}-3`

#### Scenario: Sequence never reuses
- **WHEN** destination `{clusterId}-2` is removed, then a new destination is added
- **THEN** the new destination SHALL get ID `{clusterId}-3` (not reuse `{clusterId}-2`)

### Requirement: Destination address is identifier

A destination SHALL be uniquely identified by its address. Changing the address SHALL be treated as removing the old destination and adding a new one. Health state SHALL NOT be carried over when the address changes.

#### Scenario: Address change resets health
- **WHEN** user changes destination address from `http://old:8080` to `http://new:8080`
- **THEN** the system SHALL treat it as a new destination with fresh health state (`healthy: true`)

### Requirement: Frontend address-only input

The cluster form SHALL only display an address input field for each destination. The destination name/ID field SHALL NOT be shown.

#### Scenario: Create cluster form
- **WHEN** user opens the "add cluster" form
- **THEN** each destination row SHALL have exactly one text input: the address
- **AND** there SHALL NOT be a separate "target name" or "ID" input

#### Scenario: Edit cluster form
- **WHEN** user opens the "edit cluster" form for an existing cluster
- **THEN** each destination row SHALL show the address as the primary content
- **AND** the auto-generated ID SHALL be stored as a hidden field (not displayed to user)
